# 编码规范

> 团队代码风格与编程约束的挂载点，被 `code`（编码时加载）与 `agents/code-reviewer.md`（「约定与安全」视角）引用。
>
> 本文件只保留**通用**代码约束（随 harness 分发时只有骨架与少量默认基线，带「默认基线」标注），其余内容由项目在实战中经 `record` 沉淀填充，沉淀规则见 `record-rule.md`。
>
> **语言/技术栈特定约束不放在本文件**，拆分为独立规则文件 `coding-standards-<语言>.md`（如 `coding-standards-python.md`），按需新建：项目用到某语言且出现沉淀需求时才创建，未新建即表示该语言无项目级约束。
>
> **Git 相关约定不放在本文件**：分支命名与提交信息见 `git-standards.md`，操作边界与安全禁令见 `git-boundary.md`。
>
> **没有实质条目的小节不构成任何约束**——未沉淀的维度，编码与评审一律以「严格模仿仓库中已有代码的模式」为默认基线（见 `code` 命令）。

## 通用规范

### 命名约定

命名通用基线见 `harness/rule/naming.md`（简洁、有区分度、用常见词；代码标识符谨慎使用缩写）；项目可在此追加更具体的命名约束。

（项目沉淀前除上述基线外为空）

### 代码风格

- 复杂函数内，鼓励新建临时变量来使逻辑清晰
- 内部函数尽量跟在调用者的后面，方便查看
- 函数职责内聚：一个函数围绕单一目标组织；能一套循环完成的数据处理不拆成多套循环
- 减少 `if` 嵌套：优先早返回、卫语句与条件抽取，避免多层缩进

### 注释规范

- 复杂函数必须注释：说明意图、取舍与不易察觉的边界，重点解释**为什么这样实现**（约束来源、关键分支的动机），而非复述代码做了什么
- 望文知义的逻辑不加注释，优先通过清晰的命名与结构让代码自解释

### 数据获取

- 一次请求内对同一数据源只获取一次：首次获取后通过参数或上下文传递给后续逻辑复用，禁止在多层调用中重复查询/读取

### 状态标志

- **一个标志只表达一个语义**：同一轮处理里「条件命中」与「已执行动作」用独立变量（如 `dup` / `emitted`）；复用单标志会在空集合首次处理时把「已追加」误判为「已存在」而跳过

### 结构化数据回写

- **按整条记录缓冲再替换**：修改 YAML/JSON/INI 等结构化文本时，逐行解析并整条缓冲条目，命中复合键后整条原位替换，字段顺序不影响匹配
- **注释与空行不并入条目**：条目缓冲遇到注释/空行即收口并原样输出，替换条目时不误删
- **未命中才追加**：新增条目写目标区块末尾，不覆盖相邻条目
- **写后校验**：回写完成后确认目标条目存在且无重复，不以写入命令退出码作为唯一依据

### 异常与日志

- 异常分支必须记录日志，禁止静默吞掉异常
- **批处理的跳过必须可见**：无法处理的文件/条目要显式分类或提示并交用户裁决，禁止 `continue` 后无声丢弃
- 异常日志须携带足够排查信息：关键入参、业务标识（如订单号/用户 ID）、当前状态、失败原因与可定位的位置，避免「操作失败」式无信息量文案

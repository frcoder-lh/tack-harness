# 命名规则

> 适用范围：目录名、文件名、分支名、函数名、变量名、命令名、工作流名等一切需要命名的地方。命名前先读本文件；命名是意图明确后的最后一步，不得带着模糊目的直接命名。

## 核心原则

1. **简洁**：用最短且不损失信息量的名字；能两个词说清就不用三个词。
2. **有区分度**：在同一目录、同一模块或同一上下文里不与他人重名、不易混淆；避免只靠层级才能区分的同义名。
3. **用常见词**：优先选择业界通用、队友一看就懂的词，不用生僻词、内部黑话或自造词。
4. **先看现有约定**：优先沿用仓库/项目里已有的命名方式和术语；同一概念只保留一套叫法。
5. **表达意图而非实现细节**：名字描述「是什么/做什么」，不写临时的实现手段或本次改动的过程。

## 缩写

- **允许业界通用缩写**：如 `api`、`id`、`url`、`http`、`db`、`mq`、`auth`、`cfg`、`repo`、`env`、`info`、`msg`、`ctx`、`tmp` 等；不确定是否通用时写全称。
- **项目 wiki 的文件名、目录名、分类名与分支名：鼓励使用通用缩写**，换取更短、更好扫读的路径；缩写仍需在上下文中可辨识。
- **代码中的目录、文件、函数与变量：谨慎使用缩写**，除上述公认缩写外一律写全称；不用单字母命名（循环下标等局部惯用除外）。
- **禁止自造缩写**、拼音首字母缩写与只有作者本人懂的简称。

## 分场景约定

| 场景 | 约定 |
|------|------|
| 工作区目录 / 分支 | 分支 `<type>-<username>-<description>`（见 `harness/rule/git-standards.md`）；工作区目录为 `<YYYYMMDD>-<扁平化分支名>`，由脚本生成 |
| 工作区 story 目录 | 英文小写 kebab-case，按「完整闭环功能」命名（如 `login-validation`）；多 story 时任务 ID 以 story 目录名为前缀 |
| 项目 wiki 分类目录 | 优先用短词或通用缩写（如 `biz` / `code` / `rule` / `config` / `history`）；新增分类名需能一眼看出收录范围 |
| 项目 wiki 文件名 | 英文小写 kebab-case，按主题命名，一个主题一个文件；优先短名与通用缩写（如 `repo`、`cfg`、`env`） |
| 代码目录 / 文件 | 遵循仓库既有语言与框架约定；优先复用现有目录语义，不新造平行目录 |
| 函数 / 方法 | 动词或动宾短语，说明做什么；避免 `doSomething`、`handleData`、`process` 等无信息量的泛名 |
| 变量 / 字段 | 名词，说明存的是什么；布尔值用 `is/has/can/should` 前缀；避免 `data`、`temp`、`obj`、`flag` 等无语境名 |
| 命令 / 工作流 | 单一意图的动词或动宾短语；触发词覆盖中英文常用说法，名称在全部路由中唯一 |

## 泛名与同义名

- 不单独使用 `utils`、`common`、`helper`、`manager`、`service`、`base` 等无范围限定的泛名；必须带上限定语（如 `git-commit-helper`、`wiki-index`）。
- 同一概念不在不同位置使用多套叫法（如同时出现 `config` 与 `cfg`、`history` 与 `archive`）；确需区分时在命名中体现差异。
- 不把编号、日期、人名等易变信息写进长期名称；工作区目录的日期前缀由脚本统一生成，不手工添加。

## 命名后的自检

- 不看实现，能否仅凭名字判断用途与作用域？
- 放进同级目录/同一模块，是否与已有名字冲突或难以区分？
- 是否用了生僻词、自造缩写或与项目术语不一致的叫法？
- 是否比必要的更长？能否删词而不损失含义？

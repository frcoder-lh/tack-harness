# 记录内容分类判据

> 被 `record` 命令引用：收到待沉淀内容后，按本文件判据归入五类之一，再按对应规则落盘。

## 准入前提

- 记录内容必须有明确、可复用的价值；**一次性过程信息不记录**

## 五类内容与判据

| 类型 | 收录内容 | 判据 |
|------|----------|------|
| **agents** | 项目级常驻约定：每次会话/每条指令都应遵守的行为约定与环境约束（如「本机执行 harness 脚本必须走 run.ps1」「禁止直接改主仓库」「提交信息必须带工单号」） | **需要常驻上下文、违反即出错**的规矩 |
| **cmd** | 新命令，或对现有命令流程的修改 | 可复用的命令流程能力 |
| **workflow** | 新工作流/状态机，或对现有工作流的修改 | 可复用的工作流状态机 |
| **rule** | 编码规范、研发规则（代码风格、评审要求等） | 仅在编码/评审活动中加载 |
| **wiki** | 跨工作区复用、且代码不应作为真源的知识（按需检索） | 代码外事实 / 稳定导航锚点 / 业务背景 / 技术决策与工程约定 |

## wiki 内部的四类分工

- `wiki/manifest.md`：**代码外事实**——租户、账号（不含凭据明文）、环境配置、中间件/平台地址
- `wiki/code-understanding.md`：**稳定导航锚点**——业务术语 ↔ 检索关键词/代码入口、接口标识 ↔ 业务场景 ↔ 代码入口
- `wiki/business-understanding.md`：**业务背景知识**——业务线背景、术语的业务释义、原始业务资料
- `wiki/decisions.md`：**技术决策与工程约定**——代码外的项目级「就这么定」：选型取舍（ADR）、舍入/重试/默认值等工程约定（来源通常是 plan 决策记录、git history、用户引导）
- 边界：易变的代码实现逻辑、调用链、模块内部行为**不进 wiki**（以代码为唯一真源；临期分析放 `$work/wiki/`）；通用编码规范进 rule，不进 decisions

## 类型存疑时的路由

按「常驻约束 → agents；编码规范 → rule；事实/锚点/业务知识/决策约定 → wiki；可复用流程 → cmd/workflow」归类，并向用户确认。
「某个代码外规则算 rule 还是 decisions」存疑时：跨项目通用的编码/评审规范 → rule；仅本项目成立的技术决策与工程约定 → decisions。

# 需求归档规则

> 被 `close` 命令引用：关闭工作区时判断本工作区是否有归档价值，并把需求沉淀到项目 wiki 的历史归档目录，供日后回忆「为什么做这个需求、某个点为什么这样实现」，排查问题时判断「是否设计如此」。

## 落点与命名

- 目录: `$root/wiki/<project>/history/`，不存在时先 `mkdir -p`
- 文件: 每个需求一份 md，文件名即需求名
- 需求名取已确认的明确名称（spec/plan 标题或用户确认的描述）；没有明确名称时用 `work_id`（即分支名）
- 文件名中的 `/`、`\` 等路径分隔符替换为 `-`
- 同名文件已存在时：同一需求（同一 `work_id`/分支或同一来源）就地融合更新；不同需求同名时追加 `-<YYYYMMDD>`，仍冲突则请用户确认名称，不覆盖
- 文件结构按 `harness/template/wiki-history.md`，关键结论带来源

## 归档判定（自动）

满足任一即归档：

- 有真实需求背景与功能交付，且存在需要日后回忆的「为什么」——功能取舍、边界约定、关键讨论、设计决策
- 改动了业务行为、对外接口、数据结构、配置、权限或跨服务协作
- 排查问题时可能被问到「这是设计如此还是缺陷」

不归档：

- `workflow: branch-op`：只做分支搬运，不产生业务改动与需求上下文
- 无真实 input、无 spec/plan，且只做机械性、格式性或一次性改动，没有需要回忆的背景与决策
- 内容只能从代码、提交历史或当前文档直接重建，归档只会重复代码事实
- 用户明确放弃归档

判定结果用一句话告知用户；不归档不生成空文件，不阻塞关闭。

## 归档内容

按模板写以下部分，全部用业务语言、分条陈述、简练准确：

1. **需求信息**：需求名、工作区、归档日期、状态（confirmed / candidate）、涉及服务/仓库
2. **原始资料**：需求输入文档的链接或位置（`meego`、`tech_doc_url`、input.md 中的原始链接）；只登记链接，不复制原文；无链接时注明来源
3. **实现的功能**：这个需求最终实现了哪些功能，对照 spec 故事/验收标准与 done tasks
4. **关键讨论与决策**：为什么这样做、比较过什么、放弃了什么、有哪些边界约定
5. **对系统的影响**：涉及的服务/模块、接口与数据、配置与权限、上下游依赖、兼容性与风险
6. **排查索引**：常见现象/问题 → 当前设计结论 → 是否设计如此 → 依据

## 不写什么

- 具体实现过程：编码步骤、文件/行号、调用链、模块内部实现、类与方法细节——代码是唯一真源
- 可行性分析、找 bug 的推理过程、失败尝试、测试执行日志、临时结论
- spec/plan 全文；只提炼「为什么」与「影响」
- 工作区级参数（MR 地址、泳道、构建版本）——留在 `$work/status.yaml`，随工作区关闭
- 凭据明文、无法从工作区产物证实的结论

## 审阅与来源

- 展示归档路径与内容摘要，经用户确认后生效
- 关键结论标注来源：`space/<workspace>/<文件>#<章节>`、`commit <short-hash>`、用户口述日期或原始资料链接
- 同一需求后续再次归档时就地融合更新，不重复建文件；结论变化保留「此前为 X，于 <日期> 因 <来源> 修正」轨迹
- 来源链、矛盾演变与禁写凭据要求同 `harness/rule/record-wiki.md`

# Diagnosing Bugs — Bug 诊断

针对棘手 bug 或性能回归的纪律性诊断流程。

## 阶段 1：构建反馈循环

**这是核心。** 如果你有一个**紧凑的**通过/失败信号，可以针对这个 bug 变红，你就能找到原因。花不成比例的精力在这里。

### 构建反馈循环的方法（按顺序）

1. **失败的测试** — 在触及 bug 的接缝处：单元、集成、端到端
2. **Curl/HTTP 脚本** — 针对运行中的开发服务器
3. **CLI 调用** — 使用固定输入，diff stdout 与已知良好的快照
4. **无头浏览器脚本** — 驱动 UI 并断言 DOM/控制台/网络
5. **重放捕获的追踪** — 保存真实请求，隔离重放
6. **最小化 harness** — 启动系统最小子集练习 bug 代码路径
7. **属性/模糊循环** — 运行 1000 个随机输入
8. **二分法 harness** — 在已知状态间自动化 bisect

### 收紧循环

将循环视为产品。一旦有了循环，**收紧**它：
- 能更快吗？
- 信号更清晰吗？
- 更确定吗？

## 阶段 2：复现 + 最小化

运行循环，看着它变红。确认：
- 循环产生的是**用户描述的**故障模式
- 故障在多次运行中可复现

最小化：缩小到**仍然变红的最小场景**。一次一个地切割输入、调用者、配置和步骤。

## 阶段 3：假设

生成 **3-5 个排名假设**。每个假设必须是**可证伪的**：陈述它做出的预测。

格式："如果 <X> 是原因，那么 <改变 Y> 会使 bug 消失/<改变 Z> 会使 bug 更严重。"

在测试前展示排名列表给用户。

## 阶段 4：插桩

每个探针必须映射到阶段 3 的具体预测。**一次只改变一个变量。**

## 阶段 5：修复 + 回归测试

在修复之前写回归测试，但只有在存在**正确接缝**时才写。

## 阶段 6：清理

- [ ] 原始复现不再复现
- [ ] 回归测试通过
- [ ] 所有调试插桩已移除
- [ ] 临时原型已删除

# testcode 单元测试（按需命令）

> **按需触发，不是 development 主链路的必经环节**：code 完成后可直接 commit/push，AI 不主动询问"是否跑单测"；仅当用户主动表达（如"跑单测/补测试/单测审查"）或进入 testing 工作流时才执行本命令——进入即代表要执行，不再做"是否执行/跳过"确认。
> 也是 testing 工作流的核心执行命令。
> **定位**：testcode 不只是"补单测冲覆盖率"——它是**以单测为手段的代码审查**：对照需求与代码实现找不一致、找潜在缺陷、找遗漏的边界 case，用测试暴露问题后修代码，而不是用测试去适配代码。

## 前置准入条件

- 已确定当前工作区 `$work`
- 目标任务已有实现代码（位于 `$work/repo/`）
- 仓库具备可运行的测试与覆盖率工具；没有时先与用户确认引入方式，不擅自增加重型依赖

## 核心原则

1. **单测是手段，不是目的**：覆盖率达标是准出指标之一，但更重要的是通过设计能暴露问题的用例，发现代码与需求的不一致、潜在缺陷与边界遗漏
2. **断言对准 spec/plan 的预期，而不是代码的当前行为**：当代码行为与需求预期冲突时，**修代码，不改测试**；除非经用户确认需求理解有误
3. **不为覆盖率写无效断言**：不写"跑过就行"的用例（如空断言、断言实现细节而非行为）；不可测代码需说明原因并记录

## 输入源与加载

输入源统一口径、三级降级与防循环放大遵守 `harness/workflow/development-workflow.md`「上下文加载原则」节与 `harness/rule/context-loading.md`。本环节特化：上一阶段产物取 `$work/plan.md`（测试策略提要、任务验收标准）与 `$work/spec.md`（业务规则与验收标准）；事实源为本任务代码 diff 与被测源码；按任务 ID/关键词定位被测代码与已有测试（命名如 `*Test`、`*_test`、`*.spec`）

## 指令内容

1. **确定范围并回写状态**
   - 输入: 任务 ID（未指定则取最近完成、尚未补测试的任务）
   - 动作: 从 status.yaml 的 `tasks` 与代码 diff 圈定本任务新增/修改逻辑；执行 `sh $root/harness/script/work-status.sh $work/status.yaml set stage testcode task "<任务ID>" next "需求-代码一致性审查 + 缺陷发现 + 覆盖率达标"`

2. **需求-代码一致性审查**（核心，先于写测试）
   - 输入: spec 的业务规则/验收标准 + plan 的测试策略 + 被测代码
   - 动作: 逐条核对 spec/plan 的验收标准与代码实现，识别：
     - **未实现**：需求要求的行为代码里没有
     - **实现偏差**：代码行为与需求预期不一致（返回值、错误处理、边界值、时序等）
     - **遗漏边界**：空值、极值、并发、错误恢复、超时、资源释放等场景未处理
   - 输出: 审查发现清单（需求条目 → 代码位置 → 问题类型 → 待验证），作为编写测试的依据
   - 边界: 不臆造需求；需求存疑时向用户确认，不自行脑补

3. **缺陷与边界分析**（核心）
   - 动作: 基于审查发现，针对每个潜在问题设计**能暴露该问题的测试用例**——先思考"什么输入会让这段代码出错"，再写用例验证；覆盖核心分支、边界条件、异常路径、并发与资源场景
   - 原则: 用例要对准"需求预期行为"，而非"代码当前行为"；预期代码会失败的用例也要写（确认 bug 存在），修代码后再跑通

4. **生成、运行与修复循环**
   - 动作:
     1. 先加载 `harness/rule/coding-standards.md` 中已有实质条目的小节（空小节跳过；存在 `coding-standards-<语言>.md` 时一并加载）；按需参考 `reference/tdd.md` 与 `harness/template/test-plan.md`
     2. 编写测试（模仿仓库已有测试风格），运行测试——**预期会暴露第 2/3 步发现的问题**
     3. 用例失败即确认缺陷存在：**修代码**（而非改测试去适配），修完重新运行直到通过
     4. 运行覆盖率统计，对未覆盖的**有意义分支**继续补用例；不可测代码向用户说明原因并记录
   - 重复「审查 → 设计暴露问题的用例 → 运行 → 修代码 → 回归」，直到需求-代码一致、发现的缺陷已修复、**新增/改动代码覆盖率达到 90%**

5. **审核与回写**
   - 动作: 输出：
     - 审查发现与缺陷修复清单（需求条目 / 问题 / 修复 commit 或位置）
     - 新增用例清单与覆盖率结果（前后对比）
     - 未覆盖行及原因、确认不可测的代码说明
   - 用户审核：测试是否对准需求预期、是否存在为覆盖率写的无效断言、缺陷修复是否到位
   - 通过后执行 `sh $root/harness/script/work-status.sh $work/status.yaml set progress.testcode true next commit`

6. **部署验证登记（按需）**
   - 输入: 用户是否需要部署到环境泳道做联调/验证（部署动作在外部平台执行，本命令不代为部署，只登记事实）
   - 动作: 部署完成后把泳道事实登记到 `$work/status.yaml` 的 `deploy` 区块（结构见 `harness/template/work-status.yaml`）：repo / env / lane（建议从 work_id 派生）/ route / build / url / status；环境拓扑与泳道申请方式不明时查 `$root/wiki/manifest.md`「部署环境与泳道」，缺失则提示用户补充并经 `record` 沉淀
   - 边界: 只登记事实与链接，不臆造环境信息；`deploying/deployed` 状态的泳道在 `close` 时会检查回收

## 框架自动提交（无需用户操作）

- 动作: 执行 `sh $root/harness/script/space.sh commit $root "chore(tack): workspace state <branch>"`，把本命令对 status.yaml 的变更自动提交到 tack 空间根仓库；无变更自动跳过
- 边界: 遵守 `harness/rule/git-boundary.md`

## 后置完成检验

- [ ] 已完成需求-代码一致性审查：spec/plan 验收标准逐条核对，发现的不一致已修复或向用户说明
- [ ] 已识别并修复潜在缺陷与遗漏边界（有修复清单或说明无问题）
- [ ] 测试断言对准 spec/plan 预期行为，未用测试适配代码的错误行为
- [ ] 全部新测试通过且无稳定性问题；未为覆盖率写无效断言
- [ ] 新增/改动代码覆盖率 ≥ 90%（例外已向用户说明并记录）
- [ ] 用户已审核测试质量与缺陷修复；status.yaml 已同步（progress.testcode=true）
- [ ] 已按需登记 `deploy` 泳道（或用户确认无需部署验证）

## 下一步建议

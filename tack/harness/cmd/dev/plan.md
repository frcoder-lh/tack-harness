# plan 开发计划（详细设计 + 任务拆解）

> development 工作流 planning 环节：把已确认的 spec 落成「先做什么、再做什么、每环节怎么编码」，并拆解为模块与任务。
> 细节集中在 plan.md；任务状态流转记在 status.yaml 的 `tasks` 列表。
> **关键目标**：所有需要用户决断的问题必须在本环节解决，让后续 code 阶段尽量不打扰用户。

## 前置准入条件

- 已确定当前工作区 `$work`
- `$work/spec.md` 存在且已经用户确认（`progress.spec: true`）
- 执行前重新读取 `$work/status.yaml` 与 spec.md，尊重本地最新内容

## 输入源与加载策略（节约 token）

按优先级：

1. **上一阶段产物**：`$work/spec.md`（整体设计、边界、验收标准）
2. **`$work/input.md`**：原始需求（查 spec 未覆盖的背景细节时 grep 定位）
3. **`$root/wiki/`、`$work/wiki/`**：公共知识与工作区代码理解产物（ask 产物优先）
4. **代码事实**：`$work/repo/<repo-name>/` 现有代码（数据模型、接口、配置、**可复用的类似逻辑**）

**加载纪律**：遵守 `harness/rule/context-loading.md`；关键词从 spec.md 提炼（模块名/服务名/接口名/实体名）；**额外搜索是否已有类似实现**（同名/近义类、工具方法、既有模式），为「复用优先」收集依据

## 指令内容

1. **回写环节状态**
   - 动作: 执行 `sh $root/harness/script/work-status.sh $work/status.yaml set stage plan next "生成并确认 plan.md"`（自动刷新 updated_at）

2. **收集链路信息与可复用资产**
   - 动作: 按「输入源与加载策略」定位并阅读 spec 圈定系统的代码事实（数据模型、接口、配置位置），不改动主仓库
   - 输出: 一份「已有可复用资产」清单（类似逻辑、工具类、配置模式及其文件路径），后续设计优先复用或模仿
   - 按需参考 reference: `domain-modeling.md`、`codebase-design.md`、`research.md`、`to-tickets.md`

3. **生成 plan.md 主体**
   - 输入: spec.md + input.md + wiki/代码事实 + `$root/harness/template/plan.md`
   - 动作: 按模板在 `$work/plan.md` 输出：
     - 需求理解（关键约束与假设）
     - 开发环节与顺序（环节、仓库/模块、依赖、产出）
     - 业务整体逻辑（流程、状态、规则分支）
     - 数据层：实体对象、配置项（如 TCC/配置中心/特性开关）、数据变更
     - 逻辑层：领域服务、关键算法、事务一致性、异常分支
     - 接口层：接口/方法、入参出参、上下游调用
     - 逐环节编码落地：改动文件范围、实现要点、自测方式、风险与回滚
     - 测试策略提要

4. **方案对比与选定（复杂任务门禁）**
   - 复杂度判定:
     - **可跳过**：单模块改动、存在明确可模仿的既有模式、无架构分歧的任务——一句话说明判定理由后直接采用推荐方案，仍在 plan.md 记录最终方案
     - **必须多方案**：跨模块/多仓库协作、存在两种以上合理实现路线、影响既有架构或公共接口、含非平凡数据结构/事务/兼容性变更
   - 动作（必须多方案时）:
     - 先读取 `$root/harness/agents/code-architect.md`，通过 Task 子代理**并行委派 2-3 个 architect 实例**，分别持「最小改动 / 干净架构 / 务实平衡」取向独立出方案；委派 query 须包含仓库路径、spec 关键要求、第 2 步的可复用资产清单与只读约束
     - 主 AI 汇总各方案，在 plan.md「方案对比与决策」小节输出：
       - 每个方案：核心思路、改动清单（新增/修改文件与模块）、数据与接口变更、构建顺序、Pros/Cons、风险与回滚（格式要求见角色文件）
       - **方案对比表**：对比维度至少含改动面、复用度、可维护性、兼容影响、工作量、主要风险
       - **明确推荐一个方案并给出理由**（结合代码事实与项目现状，不做无立场罗列）
     - 提交用户选定：说明推荐理由，请用户确认推荐方案或指定其他方案（也可要求补充方案）；**用户未选定前不进入模块划分**
   - 边界: 本步骤处理架构级路线选择；实现级的局部选择（异常策略、配置方式、命名等）仍归第 7 步决策点

5. **模块划分（低耦合优先）**
   - 动作: 将需求拆为**若干尽可能独立的模块**，在 plan.md 输出模块划分表：
     - 模块 | 职责（单一） | 所属仓库 | 对外暴露（接口/事件） | 依赖的模块 | 可复用资产
   - 原则:
     - 不相关的模块之间耦合越低越好：只通过明确的接口/事件交互，避免共享内部实现
     - 每个模块可独立开发、独立验证、独立演示
     - 模块内部可再拆垂直任务；模块间依赖必须形成有向无环图
   - 标注模块依赖图（文本形式，如 `A → B` 表示 B 依赖 A）

6. **逐级拆解任务**
   - 动作: 按「模块 → 特性 → 任务」拆到可独立开发、可独立验证的粒度；按 `$root/harness/template/plan.md` 的「任务清单」章节在 plan.md 末尾成稿（拆解方法按需参考 `reference/to-tickets.md`）
   - 每个任务标注：ID（建议按模块分组，如 `A-01`）、标题、所属模块/仓库、**依赖任务（deps）**、验收标准、是否可与其他任务并行
   - 无依赖的任务可并行；同模块内任务通常串行

7. **决策点前置（必须在本环节关闭）**
   - 动作: 穷举开发中可能出现的选择（技术选型、方案分支、边界处理、异常策略、配置方式等），在 plan.md 设「决策记录」小节
   - 对每个决策点：给出**推荐方案 + 理由**，能依据代码事实或最佳实践确定的直接定为结论；确实需要业务/用户决断的，列给用户一次性确认
   - 约定：code 阶段若再遇本清单外的多方案选择，AI 自动按工程最优解实现并在提交说明中记录，不中断开发
   - 分工: 架构级路线已在第 4 步关闭，本步骤只收实现级局部选择，不重复方案对比

8. **同步任务清单到 status.yaml**
   - 动作: 将任务清单写入 `$work/status.yaml` 的 `tasks` 列表（直接编辑 YAML），每条结构：
     ```yaml
     tasks:
       - id: "A-01"
         title: "<任务标题>"
         module: "<所属模块>"
         repo: "<所属仓库>"
         deps: []              # 依赖的任务 ID
         acceptance: "<验收标准>"
         parallel_with: []     # 可并行的任务 ID（信息性，调度以 deps 为准）
         status: "pending"     # pending / in_progress / done / blocked
     ```

9. **澄清与确认（人类审阅关口）**
   - 动作: 与用户逐条确认**第 4 步选定的实现方案**、技术取舍、模块边界、任务粒度与第 7 步的待决策项；用户确认前不进入 code

10. **回写完成状态**
   - 动作: 执行 `sh $root/harness/script/work-status.sh $work/status.yaml set progress.plan true next "执行 tech-design（或直接 code）"`

## 框架自动提交（无需用户操作）

- 动作: 执行 `sh $root/harness/script/space.sh commit $root "chore(tack): plan <branch>"`，把 plan.md 与 status.yaml（tasks）的变更自动提交到 tack 空间根仓库；无变更自动跳过
- 边界: 遵守 `harness/rule/git-boundary.md`；代码仓库的提交仍由 `commit` 命令执行（自动生成提交信息后直接提交，无需二次确认）

# ask 流程：回答新问题

## 0. 术语与归属定位

- 按 `harness/rule/wiki-read.md` 先定位项目 wiki：优先查 `$root/wiki/<project>/biz/glossary.md` 与 `$root/wiki/<project>/code/anchors.md`，命中术语定义或现成锚点就以该锚点为检索入口，未命中再进代码检索
- 先明确术语归属的仓库/服务（如「模型 → project + idl；报告口径 → report」），一次只进归属对应的仓库，不在多个仓库之间并行盲搜

## 1. 判断事实类型与检索入口

- 按 `harness/rule/wiki-read.md`「检索准确性」先定事实类型再选入口，精确符号优先、默认排除测试与生成代码
- 问题过宽（如「讲讲这个项目」）时先追问聚焦，或转入「整体分析」流程

## 2. 一轮并行检索

- 按「明确文档路径 → 当前主题文档 → 项目索引 → 历史归档 → 代码补查」收集信息；文档与代码路径先确定，再搜索
- 代码检索顺序：`$work/repo/<repo-name>/` 优先，缺失时 `$root/repo/<repo-name>/`（只读）
- 先限定仓库、目录与生产文件，再搜精确符号；无命中时逐级扩大范围，不因一次无命中断言不存在
- 结构/链路类问题（字段/模型从哪来、到哪里去）按「IDL struct → 库表 struct → 创建/写入 service → 消费方」顺序检索，先定链路起点与终点，再补中间环节
- 搜索命中只用于定位，不当作结论

## 3. 读取证据并形成结论

- 证据纪律按 `harness/rule/wiki-read.md`「检索准确性」（读取对应片段、逐项对应、否定结论写明检查范围、读不到标「待确认」）
- 目标文件超过 800 行时，先用 `grep -n '^func'`（或 `'^type'`）建立符号索引，再按命中行段读取；禁止边试读边回头翻找

## 4. 定位主题文档

- 按 `command-context.sh analysis` 的 `DOC` 行（主题）判断问题是否属于已有文档；不按固定文件名或 `-analysis` 后缀匹配
- 命中同一主题：在该文档中追加（见第 5 步）；存在多个相近文档无法确定时，列出候选请用户选择
- 无匹配：新建文档，文件名按主题提炼英文 kebab-case（如 `order-timeout-flow.md`，遵守 `harness/rule/naming.md`），写入 `$work/doc/analysis/`（必要时先 `mkdir -p`）；用户可改名
- 新文档初始结构：头部按 `cmd/dev/ask.md`「分析文档头部」，正文如下：

  ```markdown
  ## 梳理结论

  （问答中持续融合更新的结论区）

  ## 问答记录
  ```

## 5. 回答并融合文档

- 当场向用户输出回答，关键结论附 `仓库/路径#L12-L15` 依据
- 在「问答记录」下追加 `### Q<n>: <问题>（<日期>）` 与回答（含依据锚点）
- 同步更新「梳理结论」：新结论融合进已有表述，重复内容合并、结论变化就地更新，不堆叠矛盾说法
- 更新头部「最近更新」「涉及仓库」，并按各仓库当前 HEAD 更新「基准 commit」；`BASE` 行为 `stale` 时先提示早期结论可能基于旧代码
- 回答末尾整理 3-5 条「术语 → 检索关键词 → 代码入口」锚点候选，交 `record` 沉淀到 `code/anchors.md`；本次命中的术语（如「模型」「问卷」）可直接补上对应锚点缺口
- 边界: 主题文档留在 `$work/doc/analysis/`，不登记长期索引；易变实现细节不提炼成锚点，用户确认有稳定导航价值时走 `record`；关闭工作区时由 `close` 按 `harness/rule/archive-ask.md` 转化归档

## 6. 输出预算

- 聊天只给速览：结论、关键依据锚点与主题文档链接；细节、完整证据链与问答记录留在主题文档，聊天不复述全文

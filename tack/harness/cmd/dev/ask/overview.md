# ask 流程：整体分析

## 1. 确定范围与新鲜度（一轮并行）

- 范围: 参数指定仓库名；未指定时先遍历 `$work/repo/` 下已创建的 worktree，没有时遍历 `$root/repo/` 下全部仓库
- 并行取回: 目标仓库路径与 `git status`；`command-context.sh analysis` 输出（入口已取回时复用）
- 新鲜度: 按目标仓库的 `BASE` 行判定
  - `fresh`：提示文档最新，询问直接复用还是重新分析
  - `stale`：提示「既有分析基于 <基准>，当前已偏离 N 个提交」（N 取落后提交数），询问增量更新还是重新分析
  - 无对应文档或 `unknown`：正常进入分析（冷仓库，work 开场通常已建议执行本命令）

## 2. 检索既有知识（与代码分析并行）

- 按 `harness/rule/wiki-read.md` 检索项目 wiki（含 `history/`）与工作区文档，只读命中小节
- 历史归档只取「实现的功能 / 关键讨论与决策 / 对系统的影响 / 排查索引」；需要复用当时脚本时再看同目录的 `run/`
- 在每个目标仓库执行 `git log --oneline -50`（只读 commit message，不读 diff、不翻文件；用户要求更深时才对个别 commit `git show --stat`）
- 把发现的决策/约定线索逐条记下并附 `commit <short-hash>`；message 无法证实的只作线索，不直接当结论

## 3. 分析代码并生成文档

- 写入 `$work/doc/analysis/`（目录不存在时先 `mkdir -p`）；文件名按主题命名（`.md` 即可，不强制 `-analysis` 后缀）：
  - 仓库整体分析建议 `<repo-name>-analysis.md`（多仓库时各自一份），单仓库也可用 `code-analysis.md`
  - 也可按分析主题命名（如 `order-timeout-flow.md`），命名遵守 `harness/rule/naming.md`
- 文档头部按 `cmd/dev/ask.md`「分析文档头部」写全（主题写「仓库整体分析」或自定义主题）
- 章节结构（按需裁剪，无内容的小节标注「待补充」或省略）：
  1. **仓库概览**：主要语言、框架、构建工具、入口文件
  2. **目录结构**：顶层目录树 + 各目录职责说明
  3. **模块划分**：模块 | 职责 | 关键类/文件 | 说明
  4. **核心流程**：主要业务/请求的调用链路（从入口到落库/出参）
  5. **关键技术点**：设计模式、中间件使用、配置机制等
  6. **外部依赖**：依赖的服务、中间件、第三方库（含版本）
  7. **git history 线索**：近期 commit message 中出现的决策/约定线索（附 commit hash，标注「待确认」）
  8. **待确认问题**：分析中发现的不清晰之处
- 证据约束按 `harness/rule/wiki-read.md`「检索准确性」（锚点格式、逐项对应、否定结论写明检查范围）
- 边界: 本文档是绑定当前分支的**临期快照**，可以记录调用链、模块职责等实现细节；这些易变内容只留在 `$work/doc/analysis/`，**不回写项目 wiki**——项目 wiki 只接受稳定导航锚点与决策约定
- 仓库较大或可并行切维度时：读取 `harness/agents/code-explorer.md`，委派 2-3 个 explorer 实例（建议维度：入口与调用链 / 数据模型与数据流 / 架构模式与外部依赖），query 须包含仓库路径、范围、问题清单、只读约束与锚点格式；主 AI 汇总时保留各实例的证据锚点
- 小仓库或范围明确时主 AI 直接分析，仍遵守同样的只读与证据纪律
- 按需参考 reference（须经本命令引用方可加载）: `codebase-design.md`、`domain-modeling.md`

## 4. 汇总与审阅

- 列出生成的文档路径与各文档摘要，提示用户审阅；用户可直接修改，发现分析有误时重查对应部分
- 分析文档只留在 `$work/doc/analysis/`，默认不登记长期索引、不复制全文入项目 wiki；确需长期保留全文时，经用户确认迁移到 `$root/wiki/<project>/code/analysis/` 后在 `code/index.md` 登记
- 提炼稳定锚点候选（不直接写项目 wiki）：业务术语 ↔ 检索关键词/代码入口、接口 ↔ 业务场景 ↔ 代码入口，整理成候选清单交用户确认后按 `record` 沉淀
- 提炼决策/约定候选（不直接写项目 wiki）：能被 commit message 明确证实且代码本身看不出的项目决策/工程约定，附来源 commit hash，交用户确认后按 `record` 沉淀；无法证实的线索保留在分析文档「git history 线索」小节
- 关闭工作区时由 `close` 按 `harness/rule/archive-ask.md` 把稳定结论转化归档，只归档结论，不归档分析过程

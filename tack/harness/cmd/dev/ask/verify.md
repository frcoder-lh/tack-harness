# ask 流程：核实既有结论

## 1. 一轮并行取回当前事实

- 目标仓库路径、HEAD、分支与工作区状态
- 文档头部「基准 commit」；`git log --oneline <base>..HEAD` 与 `git diff --stat <base>..HEAD`
- 结论涉及的文件清单，按文件确定是否发生变化

## 2. 逐条验证关键判断

- 对文档「梳理结论」中的每条关键判断读取对应函数体、调用方或数据结构片段；不因搜索命中常量、RPC 名称就认定整套结论已复核
- 锚点失效时按符号名重新定位；跨仓库引用带仓库名，避免同名文件误定位
- 否定结论（「没有回调」「不会刷新」）检查相关调用链与写入路径，并写明检查范围
- 每条结论标记：已验证 / 已失效 / 待确认；读不到依据的标「待确认」

## 3. 修正文档

- 结论变化就地更新「梳理结论」，注明「原结论 X，当前代码 Y」；失效结论删除或降级为待确认
- 更新头部「基准 commit」与「最近更新」；需要时在「问答记录」追加核实记录
- 只修正被核实的内容，不重写整篇文档，不重新全量分析仓库

## 4. 汇报

- 输出：已核实的结论、已修正的结论、仍待确认的问题与原因
- 发现代码变化导致结论整体过时时，建议转入「整体分析」或「回答新问题」流程

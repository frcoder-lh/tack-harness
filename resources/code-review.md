# Code Review — 代码审查

对 `HEAD` 与固定点之间的差异进行双轴审查：

- **规范轴（Spec）** — 代码是否忠实地实现了原始需求/技术设计？
- **标准轴（Standards）** — 代码是否符合项目的编码标准？

## 过程

### 1. 确定固定点

用户指定的任何内容——commit SHA、分支名、tag、`main`、`HEAD~5` 等。如果未指定，询问。

捕获差异命令：`git diff <fixed-point>...HEAD`（三点比较，针对 merge-base）。

### 2. 识别规范来源

按以下顺序查找原始技术设计：
1. 当前需求的技术设计文档（`work/<branch>/harness/tech-design.md`）
2. 用户传入的路径
3. 如果找不到，询问用户规范在哪里

### 3. 识别标准来源

项目中记录代码编写方式的任何内容，如 `harness/rule/coding-standards.md`。

此外，始终应用以下**代码味道基线**（Fowler 代码味道）：

- **神秘命名** — 函数、变量或类型的名称没有揭示其作用
- **重复代码** — 相同的逻辑结构出现在多个文件中
- **特性嫉妒** — 方法访问另一个对象的数据多于自己的数据
- **数据团块** — 相同的几个字段或参数总是一起出现
- **基本类型痴迷** — 原始类型代表应该有自己类型的领域概念
- **重复开关** — 相同的 switch/if 级联在变更中重复出现
- **散弹式手术** — 一个逻辑变更迫使在许多文件中分散编辑
- **发散式变更** — 一个文件因多个不相关的原因被编辑
- **推测性通用性** — 为规范未要求的需求添加抽象、参数或钩子
- **中间人** — 类或函数主要只是转发调用

### 4. 执行审查

按顺序执行两个审查：

**规范轴审查：**
- 需求中要求的功能是否有缺失或部分实现？
- 差异中是否有未被要求的行为（范围蔓延）？
- 看起来已实现的需求中，实现是否看起来有问题？

**标准轴审查：**
- 差异违反了哪些已记录的标准？引用标准（文件+规则）。
- 发现了哪些基线味道？命名味道并引用代码片段。

### 5. 汇总

在 `## Standards` 和 `## Spec` 标题下分别呈现两个报告。**不要合并或重新排序发现**——两个轴的分离是有意的。

最后给出一行总结：每个轴的总发现数和最严重的问题。

## 为什么分两个轴

变更可能通过一个轴而未通过另一个轴：
- 遵循所有标准但实现错误内容的代码 → **标准通过，规范失败**
- 完全按照要求但违反项目约定的代码 → **规范通过，标准失败**

分别报告它们可以防止一个轴掩盖另一个轴。

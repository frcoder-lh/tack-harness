# Domain Modeling — 领域建模

在设计过程中主动构建和打磨项目的领域模型。这是**主动**的工作：质疑术语、发明边缘场景测试、在概念结晶的当下立即记录术语和决策。

## 文件结构

项目使用以下文件结构：

```
/
├── wiki/
│   ├── business-understanding.md    # 业务术语和概念
│   └── code-understanding.md        # 代码库理解
├── harness/
│   └── doc/
│       └── tech-design-template.md  # 技术决策记录
└── work/<branch>/
    └── harness/
        └── tech-design.md           # 当前需求的技术设计
```

## 会话中的工作

### 质疑术语

当用户使用的术语与现有文档中的定义冲突时，立即指出。例如："你之前将'取消'定义为 X，但你现在似乎指的是 Y。哪个是对的？"

### 打磨模糊语言

当用户使用模糊或过载的术语时，提出精确的 canonical 术语。例如："你说的'账户'是指客户还是用户？它们是不同的。"

### 讨论具体场景

当讨论领域关系时，用具体场景来压力测试。发明探测边缘情况的场景，迫使用户精确概念间的边界。

### 与代码交叉验证

当用户陈述某事物如何工作时，检查代码是否同意。如果发现矛盾，指出："你的代码取消了整个订单，但你刚才说可以部分取消。哪个是对的？"

### 即时更新文档

当术语被澄清时，立即更新 `wiki/business-understanding.md`。不要批量处理：捕获它们。`wiki/business-understanding.md` 应该完全没有实现细节。

### 节制地提出技术决策

只有当以下三个条件都满足时才提出创建技术决策：
1. **难以逆转**：改变想法的成本很高
2. **没有上下文会令人惊讶**：未来的读者会想"为什么我们这样做？"
3. **是真正权衡的结果**：有真正的替代方案，你出于特定原因选择了其中一个
